
## 三者的关系

- **Context（上下文）**是模型在当前一次调用中实际看到的信息，包括系统指令、当前问题、对话历史、工具说明和工具返回结果。上下文窗口有长度限制，因此要选择、组织和压缩信息。当前会话的轨迹属于短期上下文。
- **Memory（记忆）**把值得长期保留的用户事实或偏好存到当前上下文窗口之外，跨会话存在，并可更新。需要时再读取相关记忆放回上下文；它与当前会话的临时轨迹不同。
- **RAG（检索增强生成）**先从外部资料或记忆中检索相关内容，再把检索结果放入本轮 Context，供模型生成回答。它解决“哪些外部信息该进入有限的上下文窗口”的问题；Memory 可以是 RAG 的检索对象之一。

**长期记忆/知识库 → RAG 检索 → 本轮 Context → 模型回答**。检索质量会影响模型能看到的证据，但检索本身不等于生成回答。

## Chapter 2：Context 上下文工程

1. **上下文不只是 Prompt。** 一次模型调用通常包含 `system`（规则）、`user`（用户问题）、`assistant`（此前回复）、`tool`（工具结果）四类消息，工具定义则放在请求的 `tools` 字段。Agent 框架每轮都要组织这些内容，再送给模型。只修改提示词措辞是提示工程；决定哪些历史、工具结果和外部资料进入本轮请求，属于上下文工程。
2. **“静态前缀 + 动态轨迹”是常见组织方式。** 系统指令与核心工具定义相对稳定；用户消息、模型回复和工具结果按时间形成轨迹。把经常变化的时间、任务状态放在后面的消息中，有利于复用前面不变部分的缓存。KV Cache 缓存的是已处理 token 的中间结果，不等于能跨会话记住用户偏好。
3. **窗口大也不代表应该把所有材料都塞进去。** 上下文窗口有 token 上限，长对话和大段工具输出会占用预算；无关信息太多时，模型还可能找不到关键证据。整理上下文时，应优先保留当前目标、用户约束、已经做出的决定、失败原因和可追溯证据；重复或无关的工具输出可以删减或压缩。
4. **按需提供信息。** 工具说明、Skill 的详细内容和检索到的文档，都可以在需要时再加入上下文。这让本轮输入更聚焦，但必须保证后续步骤仍能取回必要信息。

## Chapter 3：User Memory 与 RAG

1. **短期轨迹与长期记忆的用途不同。** 轨迹记录当前会话发生过的消息和工具交互；长期记忆保存跨会话仍有用的事实、偏好与历史状态。记忆不宜逐句照搬对话，而要有选择地提取、概括并存成方便检索的形式。用户后来更改偏好时，还要考虑时间和冲突，避免旧信息覆盖新信息。
2. **Memory 的一个例子：**用户上次说“订票优先靠窗”，系统将其保存为长期偏好。下次订票时读取这条记忆，放进本轮 Context；如果用户这次明确要求过道座位，就应以当前要求为准。
3. **RAG 的流程：**先把资料分块并建立索引；收到问题后检索相关片段，将片段连同来源放入本轮上下文，再由 LLM 根据这些证据生成回答。知识库是外部存储，检索结果只是进入 Context 的一小部分，并非整个知识库都被模型“记住”。
4. **两种检索各有侧重。** BM25 等稀疏检索善于匹配准确术语、编号和错误码，但容易漏掉同义词；稠密向量检索擅长语义相近的表达，却可能漏掉必须精确匹配的字符。混合检索先合并两类候选，再重排序，可以互补。下面的实验 3-5 只验证了 BM25 这一检索环节。
5. **检索质量决定证据质量。** `recall@k` 看相关文档有没有进入前 k 个结果，MRR 看第一篇相关文档排得是否靠前。如果相关片段没被检出，生成阶段就缺少依据；因此 RAG 的效果不能只看回答是否流畅。
